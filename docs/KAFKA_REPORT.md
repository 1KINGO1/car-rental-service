# Kafka: топологія та перевірка відмовостійкості

Дата: 11.10.2026. Репозиторій: https://github.com/1KINGO1/car-rental-service

## Контур взаємодії

`booking-service → outbox_events → OutboxRelay → Apache Kafka → payment-service`

Сервіси мають незалежні бази даних. Після створення бронювання споживач асинхронно формує один платіж у статусі PENDING. Це запис платіжного зобов'язання; фактичного списання через зовнішнього платіжного провайдера немає. Наявні REST-ендпоінти збережено.

Модуль event-contracts містить спільний Java Record BookingCreated та JSON Schema v1. Обов'язкові поля: eventId, schemaVersion, eventType, occurredAt, bookingId, customerId, amount, currency. Ключ Kafka дорівнює bookingId. UUID події створюється один раз перед записом Outbox та не змінюється при повторній публікації. Поточний тариф бронювання передається в UAH. Споживач перевіряє версію, тип, обов'язкові поля, суму, валюту та відповідність ключа; невідомі додаткові поля допускаються. Несумісні зміни потребують нової версії контракту й топіка. Schema Registry не використовується.

## Атомарність і доставка

BookingService.create працює з @Transactional. Запис бронювання та OutboxRepository.append використовують один JdbcClient, DataSource і автоматично налаштований JDBC TransactionManager. Для append встановлено MANDATORY: виклик без активної транзакції заборонено. Kafka не викликається всередині створення бронювання. Збій запису Outbox або відкат зовнішньої транзакції скасовує обидва записи.

Relay щосекунди читає до 20 непереданих подій через FOR UPDATE SKIP LOCKED. Позначка published_at записується лише після успішного завершення KafkaTemplate.send. Продюсер використовує acks=all, enable.idempotence=true і max.in.flight.requests.per.connection=5. При помилці relay транзакція відкочується, подія залишається доступною для повтору. Кілька relay не забирають одночасно ті самі заблоковані рядки.

Гарантія доставки - at-least-once. Збій після підтвердження Kafka, але до commit published_at може дати повтор. Цей випадок перевірено: дві публікації містять однакові payload та eventId. Outbox не проголошує атомарної транзакції між Kafka й SQL.

Споживач виконує INSERT у processed_events з унікальним event_id та створення платежу в одній JDBC-транзакції. ON CONFLICT DO NOTHING відсікає повтори, а унікальність payments.booking_id додатково захищає бізнес-операцію. Суперечлива сума або валюта для наявного платежу спричиняє відмову. Offset підтверджується після повернення обробника, enable-auto-commit=false, ack-mode=record. Відмова після SQL commit до підтвердження offset не повторює платіж.

## Топологія

| Топік | Призначення | Партиції |
| --- | --- | ---: |
| rental.booking-created.v1 | Основні події | 3 |
| rental.booking-created.v1-retry-0 | Перша повторна спроба, затримка 1 с | 3 |
| rental.booking-created.v1-retry-1 | Друга повторна спроба, затримка 2 с | 3 |
| rental.booking-created.v1-retry-2 | Третя повторна спроба, затримка 4 с | 3 |
| rental.booking-created.v1-dlt | Ізоляція невдалих подій | 3 |

Основна група: payment-bookings-v1. @RetryableTopic створює окремі групи для retry/DLT. Максимум чотири спроби разом із початковою. Пошкоджені контракти та інші IllegalArgumentException направляються одразу в DLT. @DltHandler зберігає payload і координати DLT-запису в failed_events; первинний ключ (topic, partition_id, record_offset) захищає цей журнал від повторної обробки. Після усунення причини подію можна контрольовано перевідправити з тим самим eventId. Автоматичного нескінченного повернення DLT-подій в основний топік немає.

Порядок гарантується Kafka лише в межах партиції основного топіка. Перехід через retry-топіки може змінювати порядок завершення обробки. Для незалежних подій створення бронювання це допустимо; для послідовних змін стану потрібний окремий контроль версії агрегату.

## Експеримент зі збоями

Нові тести запускають реальний брокер через @EmbeddedKafka з трьома партиціями. Для SQL використано H2 у режимі PostgreSQL. Відмови вводяться тільки у тестах через spy-компоненти, без керованого ззовні аварійного режиму в робочому API.

| Перевірка | Очікуваний і перевірений результат |
| --- | --- |
| Запис бронювання та події | Одна сутність і один Outbox-запис; relay передає ключ bookingId |
| Відмова Outbox після INSERT | Немає ні бронювання, ні події |
| Відкат зовнішньої транзакції | Обидва записи відсутні |
| Помилка публікації | Подія залишається pending; наступна спроба успішна |
| Kafka ACK перед відкатом SQL | Повторна публікація має той самий eventId |
| Постійна відмова після запису платежу | 4 спроби, 1 запис у DLT; 0 платежів і 0 processed_events до відновлення |
| Відновлення та повтор після DLT | 1 платіж і 1 processed_events |
| Дві тимчасові відмови | Третя спроба успішна; додаткові повтори не дублюють платіж |
| Відмова після commit до offset ACK | Повторна доставка; у БД залишається 1 платіж |
| 8 конкурентних дублікатів | 1 платіж і 1 ключ обробленої події |
| Пошкоджений JSON | Ізоляція в DLT |
| Перевірка Admin API | Усі 5 топіків мають по 3 партиції |

Підсумок повної збірки: BUILD SUCCESS, 36 тестів, 0 невдач, 0 помилок, 0 пропущених. Із них 11 нових тестів перевіряють Kafka/Outbox. Час фінального прогону Maven: 40,304 с.

## Відтворення

За наявності JDK 25 і Maven запустити з кореня `mvn -B -ntp verify`. Нові набори: OutboxIntegrationTest і KafkaFailureIntegrationTest. Docker для автоматизованих тестів не потрібний.

Для запуску всього контуру заповнити локальний .env за .env.example та виконати:

```
docker compose -f docker-compose.yml -f docker-compose.kafka.yml up --build
```

Для окремого запуску сервісів задати MESSAGING_ENABLED=true, KAFKA_BOOTSTRAP_SERVERS=localhost:9092 та власні DB_URL, DB_USER, DB_PASSWORD. За вимкненого MESSAGING_ENABLED Outbox продовжує накопичувати події, але relay і Kafka-споживач не запускаються.

Локальна конфігурація має один Kafka-брокер і replication factor 1. Вона перевіряє відмовостійкість застосунків, але не забезпечує відмовостійкість брокера. Для продуктивного кластера потрібні щонайменше три брокери, replication factor 3, min.insync.replicas=2, відповідні retention, моніторинг pending Outbox, consumer lag і DLT. Автоматичне очищення Outbox та ключів дедуплікації не реалізовано; строк зберігання має покривати весь допустимий період replay.

У цьому прогоні не проводилися тривале навантаження, аварійне завершення процесів ОС або перевірка на PostgreSQL. Відмови змодельовано винятками у визначених точках транзакцій і доставки. Docker Compose підготовлено для локального запуску.

Джерела: https://docs.spring.io/spring-kafka/reference/retrytopic.html та https://docs.spring.io/spring-kafka/reference/testing.html
