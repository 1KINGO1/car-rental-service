# Захист Kubernetes у проєкті Car Rental Service

## Мета та склад роботи

Налаштовано ізоляцію мережевого доступу та обмеження привілеїв для проєкту оренди автомобілів. Підготовлено захищений Helm-chart `k8s-security` на основі наявних маніфестів мікросервісів і PostgreSQL. Він містить чотири бізнес-сервіси, чотири бази даних, шлюз, Ingress і десять NetworkPolicy. Статичні та інтеграційні перевірки пройдено. У запущеному кластері підтверджено маршрутизацію через Ingress, блокування несанкціонованих з’єднань і параметри захисту контейнерів.

Вихідні маніфести з каталогу `k8s` збережено як матеріали попередніх робіт. Для цього завдання використовується тільки `k8s-security` у namespace `car-rental-security`. Компоненти попередніх лабораторних для моніторингу, трасування та Kafka в це розгортання не включено. Обмін повідомленнями вимкнено початковою конфігурацією застосунків. У наданому архіві окремого маніфесту Ingress не було, тому його додано разом зі шлюзом.

## Маршрутизація запитів

Схема з’єднань: **клієнт → Ingress → gateway → бізнес-сервіс → власна база даних**.

Ingress приймає запити з Host `car-rental.local` і префіксом `/api`, передає їх Service `gateway:8080`. Шлюз NGINX зберігає шлях запиту та розподіляє трафік:

| Шлях | Бізнес-сервіс | Дозволена база даних |
|---|---|---|
| `/api/customers` | customer-service:8080 | customer-db:5432 |
| `/api/vehicles` | fleet-service:8080 | fleet-db:5432 |
| `/api/bookings` | booking-service:8080 | booking-db:5432 |
| `/api/payments` | payment-service:8080 | payment-db:5432 |

Внутрішні звернення booking-service до customer-service і fleet-service також проходять через gateway. Для цього змінено CUSTOMER_URL і FLEET_URL. Це дозволяє зберегти єдине дозволене джерело вхідних з’єднань до бізнес-сервісів — поди з міткою `app: gateway`.

## Мережеві політики

Політика `default-deny-ingress` має `podSelector: {}`, `policyTypes: [Ingress]` і `ingress: []`. Вона охоплює всі наявні та майбутні поди namespace. Вихідний трафік цим завданням не обмежується, тому окремий дозвіл DNS не потрібний.

Політика шлюзу дозволяє TCP 8080 від Ingress-контролера, для якого одночасно мають збігатися namespace `ingress-nginx` і pod-мітка `app: ingress-controller`. Друга дозволена група — booking-service у namespace застосунку. Селектори namespace та pod для контролера записано в одному елементі `from`, тобто обидві умови обов’язкові.

Чотири політики бізнес-сервісів відкривають TCP 8080 лише для gateway у тому самому namespace. Чотири політики БД відкривають TCP 5432 лише для відповідного власника: customer-service → customer-db, fleet-service → fleet-db, booking-service → booking-db, payment-service → payment-db. Шлюз, сторонні поди й інші бізнес-сервіси не отримують доступу до чужої БД.

Політики потребують CNI з підтримкою NetworkPolicy. Мітку `app: ingress-controller` потрібно встановити у pod template реального контролера або змінити відповідне значення chart. Контролер має працювати без hostNetwork. Інші дозвільні політики в namespace можуть розширити доступ, оскільки NetworkPolicy застосовуються сукупно. Ці властивості описані в [документації Kubernetes про NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

## Обмеження привілеїв

Усі дев’ять Deployment захищеного chart отримали pod-level `securityContext` із `runAsNonRoot: true`, числовими UID/GID та `seccompProfile.type: RuntimeDefault`. Для бізнес-сервісів використано UID/GID 10001, для шлюзу — 101, для PostgreSQL Alpine — 70. У кожному контейнері встановлено `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true` і `capabilities.drop: [ALL]`. Автоматичне монтування API-токена вимкнено через `automountServiceAccountToken: false`.

Для потрібних операцій запису залишено окремі томи. Java-сервіси використовують обмежений emptyDir у `/tmp`. Шлюз записує PID і тимчасові файли в `/tmp`, а журнали — у stdout/stderr. PostgreSQL зберігає дані в PVC, сокети в `/var/run/postgresql`, тимчасові файли в `/tmp`. PGDATA перенесено в підкаталог `/var/lib/postgresql/data/pgdata`; fsGroup надає груповий доступ до змонтованих томів. Коренева файлова система контейнерів доступна лише для читання. Для вже наявних PVC необхідно перевірити власника файлів перед міграцією.

## Середовище інтеграційного тестування

Перевірки виконано 1 листопада 2026 року в окремому локальному кластері k3s v1.33.6+k3s1, запущеному в Docker Engine 29.8.0. Використано вбудоване виконання NetworkPolicy k3s та Ingress-контролер Traefik 3.5.1. Наявні розгортання попередніх лабораторних не змінювалися.

Для цього середовища застосовано `values.k3s.yaml`: ingressClassName — traefik, namespace контролера — kube-system, app-мітка — ingress-controller. Мітку додано до pod template Traefik. Зовнішні запити надходили через локальний port-forward `18080:80` до Service Traefik, після чого проходили реальний маршрут Ingress → gateway → сервіс. Port-forward до бізнес-сервісу або БД для цих тестів не використовувався.

Образи чотирьох сервісів зібрано з вихідного коду проєкту з тегом 1.0.1. Maven завершив збірку з BUILD SUCCESS. У namespace car-rental-security готові 14 подів: по дві репліки кожного бізнес-сервісу і шлюзу та по одному поду кожної БД.

## Відтворення перевірок

Порядок розгортання наведено в `k8s-security/README.md`. Для k3s під час встановлення chart додати `-f ./k8s-security/values.k3s.yaml`. Після побудови образів із тегом 1.0.1, створення секретів та встановлення chart виконати з кореня проєкту:

```powershell
./k8s-security/tests/runtime.ps1 -IngressUrl http://127.0.0.1:18080
./k8s-security/tests/booking-flow.ps1 -IngressUrl http://127.0.0.1:18080
```

Адресу замінити фактичною адресою Ingress. Скрипт очікує готовність Deployment, перевіряє HTTP 200 для чотирьох маршрутів, фактичний non-root UID, NoNewPrivs процесу, відсутність API-токена та відмову запису в корінь контейнера. Також перевіряються параметри безпеки у специфікації запущених подів.

Для мережевих тестів створюються тимчасові поди з мітками дозволених і сторонніх джерел. Вони не отримують секретів і залишаються NotReady, щоб не потрапити до робочих endpoint шлюзу. Позитивна спроба з’єднання з кожною БД перевіряє доступність цілі; негативні спроби зі стороннього пода, шлюзу й інших бізнес-міток мають завершитися відмовою. Перевіряється також прямий доступ стороннього пода до сервісів і шлюзу. Тестові поди видаляються в блоці finally, протокол записується в `runtime-results.txt`.

Отримано повідомлення `PASS all runtime tests`. Дев’ять дозволених з’єднань охоплюють gateway → чотири сервіси, чотири власники → свої БД та booking-service → gateway. Двадцять п’ять заборонених з’єднань охоплюють сторонній pod → чотири БД, gateway → чотири БД, сторонній pod → чотири сервіси, дванадцять звернень сервісів до чужих БД і сторонній pod → gateway.

Окремий протокол `process-security.txt` підтверджує UID 101, 10001 і 70 відповідно до компонентів; CapEff дорівнює нулю, NoNewPrivs — 1, Seccomp — 2. Кореневе монтування має прапорець ro, API-токен відсутній, а запис у виділений /tmp працює.

Сценарій `booking-flow.ps1` створив тестового клієнта, автомобіль і бронювання та прочитав створене бронювання назад. Він підтвердив роботу внутрішніх викликів booking → gateway → customer/fleet і запису в PostgreSQL під активними мережевими політиками. Ідентифікатори записів містяться у `booking-flow.json`. Тимчасові мережеві поди видалено після завершення тесту.

Підтвердження стосується локального одновузлового кластера. Відмовостійкість кількох вузлів і виробниче навантаження цим тестуванням не перевірялися.

## Три сценарії відмови та способи усунення

### Перевантаження сервісів запитами

Надмірна кількість HTTP-запитів може вичерпати CPU, пам’ять, потоки обробки та пул з’єднань PostgreSQL. Ознаки: зростання затримок, HTTP 5xx, OOMKilled і перезапуски подів. Requests/limits і дві репліки бізнес-сервісів та шлюзу частково обмежують вплив, але не гарантують доступність усього кластера.

Усунення: обмежити частоту та паралельність запитів на вході, прибрати джерело навантаження, масштабувати сервіси й перевірити місткість БД. Для запобігання повторенню потрібні HPA, квоти namespace, моніторинг затримок і навантажувальне тестування. Rate limiting, HPA та квоти не включені в поточний chart.

### Втрата доступності бази даних

Кожна БД має одну репліку. Відмова її вузла, переповнення PVC або пошкодження даних зупиняє залежний бізнес-сервіс. NetworkPolicy обмежує мережевих клієнтів, але не забезпечує резервування даних. Ознаки: помилки з’єднання, Pending через том або відсутність вільного місця.

Усунення: відновити вузол або підключення тому, збільшити місткість підтримуваного PVC, відновити дані з перевіреної резервної копії. Запобігання: регулярні резервні копії з перевіркою відновлення, контроль вільного місця та PostgreSQL з реплікацією й автоматичним перемиканням. Поточний chart використовує один PVC на БД і не налаштовує резервне копіювання.

### Помилкова політика або конфігурація Ingress

Неправильна app-мітка контролера, namespaceSelector, номер порту чи backend Ingress може перекрити дозволений маршрут одразу для всіх клієнтів. Ознаки: тайм-аути, HTTP 502/504, доступні поди за відсутності клієнтського доступу.

Усунення: зіставити pod-мітки, Service selectors, EndpointSlice та правила NetworkPolicy; виправити конкретний селектор або відкотити Helm-реліз до перевіреної ревізії. Не видаляти Default Deny для постійного відновлення доступу. Запобігання: запуск lint і статичних тестів перед зміною, перевірка маршруту в окремому namespace та інтеграційні тести після розгортання.

## Залишкові ризики

Селектор app ідентифікує групу подів, але не є автентифікацією користувача. Право створювати чи перемарковувати поди дозволяє підставити дозволену мітку; його слід обмежувати RBAC. Скомпрометований бізнес-сервіс зберігає доступ до власної БД, а дозволений booking-service — до маршрутів шлюзу. Захист кореневої файлової системи не робить PVC або emptyDir доступними лише для читання. Для виробничого використання додатково потрібні автентифікація API, TLS, резервні копії та контроль вихідного трафіку.
