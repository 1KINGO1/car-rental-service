# Контрактне та навантажувальне тестування Car Rental Service

Звіт за фактичними запусками 15 листопада 2026 року. Час у таблицях — Київ (UTC+02:00); машинні логи містять UTC або явний часовий зсув.

## Результат роботи

Створено контрактну перевірку для двох реальних сервісів `booking-service` і `fleet-service`. Початковий контракт пройшов 6/6 перевірок. Несумісна зміна Protobuf лише на стороні fleet призвела до падіння 2/6 перевірок із ненульовим кодом завершення. Після відновлення контракту знову пройшли 6/6. Виконано три сценарії k6: постійне навантаження, поступове зростання та різкий пік. Сумарно виконано **34 596 вимірюваних запитів**, без HTTP-помилок і порушень очікуваного змісту; всі пороги пройдено.

## Контракт двох сервісів

Очікування споживача винесені в `tests/contracts/booking-fleet-v1.json`. Тест `test_booking_fleet_contract.py` використовує ці очікування незалежно від Java-класів, згенерованих для постачальника. Це контрактний тест на рівні інтеграції реальної пари сервісів через HTTP-фасад споживача; Pact Broker не використовується.

| Перевірка | Очікувана поведінка |
| --- | --- |
| Unary | HTTP 200, правильні UUID, марка, модель, номер і тариф 1200.00 |
| Server streaming | HTTP 200, рівно два різні автомобілі з правильними полями й тарифами |
| Client streaming | 2 позиції; `1200 × 2 + 1500 × 3 = 6900.00`; валюта UAH |
| Bidi | Дві відповіді з відповідними requestId, vehicleId, days; суми 2400.00 і 4500.00 UAH |
| Відсутній автомобіль | NOT_FOUND від fleet перетворюється booking на HTTP 422 |
| Неправильна кількість днів | Для `days=0` очікується HTTP 400 |

### Несумісна зміна лише з одного боку

У `VehicleReply` тимчасово змінено номер поля:

```proto
// Було:
string daily_rate = 5;
// Лише у збірці fleet-service стало:
reserved 5;
string daily_rate = 15;
```

Перезібрано лише fleet і його залежності командою `mvnw.cmd -B -Pgrpc-demo -pl fleet-service -am -DskipTests clean package`. Booking не входить до цього reactor selection. Компіляція завершилася успішно. Той самий booking JAR продовжив працювати зі старим номером поля, JSON очікувань не змінювався. Оркестратор перевірив незмінність їхніх SHA-256.

SHA-256 незмінного booking JAR:

```text
08632cd2d729123b45d86f85e0e1f9034cb50457a0076e131b174cb78e99fd4f
```

Зміна номера поля порушує бінарну сумісність: старий споживач не отримує очікуваний `daily_rate` під номером 5. За логікою `FleetGrpcConfiguration.vehicle` порожнє значення не перетворюється на `BigDecimal`, і HTTP-фасад відповідає 500. Правила номерів полів наведено в [офіційній документації Protobuf](https://protobuf.dev/programming-guides/proto3/#assigning).

| Фаза | Пройшло | Падіння assertions | Помилки запуску тестів | Код тесту |
| --- | --- | --- | --- | --- |
| Початковий контракт | 6/6 | 0 | 0 | 0 |
| Fleet з полем 15, booking з полем 5 | 4/6 | 2 | 0 | 1 |
| Відновлений контракт | 6/6 | 0 | 0 | 0 |

Фактичне повідомлення в обох невдалих перевірках: `AssertionError: 500 != 200`. Впали `test_unary_vehicle_contract` і `test_server_stream_vehicle_contract`; інші чотири тести пройшли. Оркестратор вимагає саме ці два падіння, а не довільний збій. Очікуваний код 1 дочірнього тесту є доказом експерименту; загальний сценарій продовжується після його перевірки. Вихідний proto відновлено побайтово, fleet повторно зібрано. У фінальному проєкті залишається сумісне поле 5.

## Три сценарії навантаження

| Сценарій | Профіль навантаження | Заданий до запуску поріг p95 |
| --- | --- | --- |
| steady | 10 VU, 45 с | < 500 мс |
| ramp | Початково 1 VU; цілі 10, 30, 60, 0; по 15 с на етап | < 1000 мс |
| spike | 5 VU / 10 с → підйом до 80 / 2 с → 80 / 15 с → спад до 5 / 3 с → 5 / 20 с | < 1500 мс; фаза відновлення < 500 мс |

Один VU виконує один запит за ітерацію та паузу 100 мс. Чергуються чотири операції з приблизно рівними частками. Для кожної відповіді перевіряються статус 200 і дані контракту. Модель закрита: при збільшенні затримки частота запитів може зменшуватися; фіксована кількість запитів за секунду не задавалася. Опис виконавців — у [документації k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/).

До вимірювань виконано 100 запитів прогріву, по 25 на кожну операцію. Сервіси не перезапускаються між сценаріями, пауза між ними — 3 с. Graceful stop/ramp-down — до 10 с. Порогові умови: HTTP-помилки < 1%, помилки змісту = 0, checks = 100%; p95 обмежено і для сукупності, і для кожної операції. Пороги навчальні, не виробничі SLA. [k6 повертає ненульовий код при порушенні порогів](https://grafana.com/docs/k6/latest/using-k6/thresholds/).

Тривалість береться з `testRunDurationMs`, частота — з `http_reqs.rate`, затримки — з `http_req_duration`. Це час HTTP-запиту до booking із внутрішнім gRPC-викликом; 100 мс паузи VU не входять до затримки запиту. p95 означає, що 95% запитів завершилися не повільніше зазначеного значення.

## Відтворення й докази

Потрібні JDK 25, Python 3.11+, k6 та Maven Wrapper із проєкту. У PowerShell у корені розпакованого проєкту:

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-25'
python scripts/run-contract-load.py --k6 'C:\path\to\k6.exe'
python scripts/summarize-contract-load.py
```

Перший скрипт виконує Maven verify, три фази контракту, прогрів і три сценарії k6. `--contracts-only` обмежує запуск контрактним експериментом; `--skip-build` використовує вже перевірені JAR. Другий скрипт незалежно звіряє кількість запитів, частки помилок і p95 із сирими метриками та створює CSV. У цьому запуску всі звірки пройдено. Деталі — `README_CONTRACT_LOAD.md`.

| Артефакт у `docs/evidence/contract-load/` | Призначення |
| --- | --- |
| `run-summary.json`, `runner.log` | Команди, часові мітки, результати фаз, незмінність booking |
| `baseline/`, `broken/`, `restored/` | `tests.log`, `result.json`, `context.json`, логи JVM |
| `mutation-build.log`, `restore-build.log` | Успішна збірка зміненого й відновленого постачальника |

| `load/steady/`, `load/ramp/`, `load/spike/` | Логи k6, повний `summary.json`, сирі `metrics.json.gz` |
| `load-results.csv`, `load-analysis.json` | Порівняння сценаріїв і розподіл за операціями/фазами |
| `maven-verify.log`, `regression-summary.json`, `hardware.json` | Регресійні тести та характеристики стенду |

## Межі результатів

Два сервіси та генератор навантаження працювали на одному Windows-хості, з H2 і plaintext gRPC. Проведено по одному короткому запуску кожного профілю. PostgreSQL, Docker, Kubernetes, TLS, Kafka та повний процес створення бронювання з customer/payment у навантажувальних сценаріях не перевірялися. Вимірювалися читання й розрахунок вартості через наявний HTTP-фасад; Bidi-час є часом зібраної HTTP-відповіді, а не окремого повідомлення потоку. Звідси не випливає гарантія продуктивності production або відсутності витоків під багатогодинним навантаженням.

Вимоги цієї роботи підтверджені кодом і фактичними запусками: контрактна перевірка двох сервісів, її падіння через односторонню несумісну зміну, три виконані профілі навантаження та збережені дані результатів.
