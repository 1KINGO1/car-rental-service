# Контрактне та навантажувальне тестування

Перевіряються **два реальні сервіси**: `booking-service` (споживач) і `fleet-service` (постачальник). Python надсилає HTTP-запити до booking, а booking викликає fleet через справжній gRPC/TCP. Обидва сервіси запускаються в окремих JVM із H2. Моки цих сервісів не використовуються.

## Вимоги та запуск

- JDK 25; `JAVA_HOME` має вказувати на його каталог.
- Python 3.11+; сторонні Python-пакети не потрібні.
- Grafana k6 (перевірено на 2.4.0), у `PATH` або через `--k6`.
- Maven Wrapper входить до проєкту; для першої збірки потрібен доступ до Maven Central.
- Вільні порти 28082, 28083, 29090; можна змінити через `--ports 28082 28083 29090`.

У PowerShell з кореня проєкту:

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-25'
python scripts/run-contract-load.py --k6 'C:\path\to\k6.exe'
```

Або передайте JDK через `--java-home`. Скрипт спочатку виконує `mvnw.cmd -B -Pgrpc-demo clean verify`, потім усі контрактні перевірки та три навантажувальні сценарії. `--skip-build` допускається лише після успішної збірки поточного коду з профілем `grpc-demo`.

Тільки контракт, включно з демонстрацією несумісності та відновленням:

```powershell
python scripts/run-contract-load.py --contracts-only
```

## Контракт і перевірка несумісності

`tests/contracts/booking-fleet-v1.json` фіксує стан постачальника та очікування споживача. `tests/contracts/test_booking_fleet_contract.py` перевіряє шість випадків: Unary, Server streaming, Client streaming, Bidi, відсутній автомобіль і неправильну кількість днів. Перевіряються статуси, ідентифікатори, поля автомобілів, суми, валюта та кількість відповідей.

Це контрактна перевірка на рівні інтеграції двох сервісів через зовнішній інтерфейс споживача; Pact Broker або Spring Cloud Contract не потрібні. Вона перевіряє спостережувану поведінку реальної пари, а не всі можливі зміни схеми.

Послідовність оркестратора:

1. Початковий контракт: 6 тестів мають пройти.
2. Змінити `VehicleReply.daily_rate` з поля `5` на `15`, зарезервувавши `5`.
3. Перезібрати лише fleet та його залежності: `-pl fleet-service -am -DskipTests clean package`. Booking JAR залишається незмінним; SHA-256 перевіряється програмно. JSON очікувань також залишається незмінним.
4. Запустити той самий тест. Очікуються рівно два падіння assertions для Unary і Server streaming, код завершення тесту `1`. Компіляційна помилка, збій запуску чи інша причина не вважаються доказом несумісності.
5. Відновити вихідний proto, перезібрати fleet і повторити 6 тестів. Усі мають пройти.
6. На відновлених сервісах виконати навантажувальні сценарії.

Очікуване падіння дочірнього тесту обробляється оркестратором як успішно підтверджений експеримент. Несподівані падіння повертають ненульовий код. При звичайному винятку скрипт відновлює proto і намагається відновити JAR. Примусове завершення самого Python-процесу посеред мутації потребує ручного повернення `daily_rate = 5` без `reserved 5` і повторної збірки. Не запускайте паралельну збірку під час цього експерименту.

## Три сценарії k6

| Сценарій | Профіль | Критерій p95 |
| --- | --- | --- |
| steady | 10 VU протягом 45 с | < 500 мс |
| ramp | 1 → 10 → 30 → 60 → 0 VU, 4 етапи по 15 с | < 1000 мс |
| spike | 5 VU / 10 с; підйом до 80 / 2 с; 80 / 15 с; спад до 5 / 3 с; відновлення 5 / 20 с | < 1500 мс; відновлення < 500 мс |

Кожна ітерація виконує один із чотирьох викликів (Unary, список, Client streaming, Bidi), перевіряє HTTP 200 і зміст відповіді, потім чекає 100 мс. Частки операцій приблизно рівні. До вимірювань виконуються 100 запитів прогріву. Між сценаріями пауза 3 с; сервіси залишаються запущеними. Це закрита модель VU, а не фіксована інтенсивність запитів.

Для кожного сценарію: HTTP-помилки < 1%; помилки контрактного змісту = 0; checks = 100%; поріг p95 діє і загалом, і для кожного виду операції. Пороги задані до запуску як навчальні критерії, не як виробничі SLA. k6 повертає ненульовий код при порушенні порогів. Оркестратор усе одно виконує інші сценарії, зберігає результати та завершується з помилкою.

## Артефакти

- `docs/report/Contract_Load_Report.md` — звіт за фактичним запуском.
- `docs/evidence/contract-load/run-summary.json` — часові мітки UTC, команди, коди завершення та SHA-256.
- `baseline/`, `broken/`, `restored/` — результати контракту, логи обох JVM, параметри підключення та UUID у `context.json`.
- `mutated-provider.proto` — несумісний варіант схеми для аудиту; робочий proto відновлено.
- `load/{steady,ramp,spike}/summary.json` — повні агрегати k6 і результати порогів.
- `load/{steady,ramp,spike}/metrics.json.gz` — сирі часові ряди всіх метрик k6.
- `maven-verify.log` — повна попередня регресійна перевірка.

Після завершення запустіть `python scripts/summarize-contract-load.py`: скрипт звірить кількість запитів, помилки й p95 із сирими метриками та сформує `load-results.csv` і `load-analysis.json`.

Повторний запуск перезаписує ці результати. Збережіть попередню копію, якщо потрібне порівняння кількох запусків. Скрипт завершує лише створені ним процеси.

## Межі вимірювань

Локальна Windows-машина, дві JVM, H2, plaintext gRPC і генератор k6 на тому самому хості. Вимірюється HTTP → booking → gRPC → fleet → H2 та відповідь назад. Створення бронювань, Kafka, customer/payment, PostgreSQL, Docker, Kubernetes і тривалі endurance-тести не входять до трьох сценаріїв. Bidi вимірюється через HTTP-фасад, який збирає відповіді; це не вимірювання часу кожного елемента прямого gRPC-потоку.

Офіційна документація: [номери полів Protobuf](https://protobuf.dev/programming-guides/proto3/#assigning), [сценарії k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/), [пороги k6](https://grafana.com/docs/k6/latest/using-k6/thresholds/).
